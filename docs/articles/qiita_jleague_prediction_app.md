# 2 システム構成

全体の処理は以下のようになっています。

```text
Jリーグ公式サイト・外部データ
        │
        ▼
試合日程・結果・チーム・選手データ取得
        │
        ▼
試合前特徴量の作成
        │
        ▼
LightGBMでホーム・アウェイ期待得点を予測
        │
        ▼
ポアソン分布から全スコア確率を計算
        │
        ├── 予測スコア
        ├── 勝敗確率
        ├── スコア候補Top 5
        └── 最終順位シミュレーション
        │
        ▼
予測結果をJSONで保存
        │
        ├── Streamlit Webアプリ
        └── GitHub Pages上のPWA
```

データ取得から予測結果の更新まではGitHub Actionsで定期実行します。

モデルはアプリの画面表示時に毎回推論するのではなく、事前に予測結果をJSONとして生成します。UIはJSONを読み込んで表示するだけの構成にしています。

この構成にした理由は以下です。

- アプリを開くたびにモデルを読み込む必要がない
- StreamlitとPWAで同じ予測結果を利用できる
- 推論に失敗しても、直前の正常な予測結果を残せる
- モデル部分とUI部分を分けてテストできる

## 3.2 使用した特徴量

サッカーの得点は、単純な順位だけで決まるわけではありません。そこで、両チームの基礎的な強さ、直近の状態、攻守の傾向、日程条件などを組み合わせました。

大きく分けると、使用した特徴量は以下のようになります。

| 分類 | 主な特徴量 | 予測に取り入れたい情報 |
| --- | --- | --- |
| 順位・勝点 | 現在順位、順位差、現在勝点、順位変化、シーズン進行率 | 現時点での成績と上昇・下降傾向 |
| 総合的なチーム力 | Eloレーティング、ホームとアウェイのElo差 | 対戦相手の強さも考慮した実力差 |
| 直近の調子 | 直近5試合の獲得勝点 | 最近勝点を取れているか |
| 当季の攻撃内容 | Rolling xG（当季ここまでの1試合平均期待得点） | シーズンを通じて質の高いチャンスを作れているか |
| 攻撃・守備指数 | AGI、KAGI | チャンス構築力と守備力 |
| チームの資産規模 | ホーム・アウェイの市場価値、市場価値差 | 選手層を含むチーム戦力の目安 |
| 日程・移動 | 休養日、アウェイ移動距離 | 過密日程や長距離移動による負荷 |
| 監督 | 監督在任期間 | チーム作りの継続性 |
| 対戦相性 | 過去の直接対戦における平均得点 | チーム同士の組み合わせによる傾向 |
| スタジアム | 収容人数 | 会場規模などの環境差 |
| フォーメーション | 両チームの布陣、DF・MF・FW人数、ミラーゲームかどうか | ピッチ上の人数配置と噛み合わせ |
| 攻守の噛み合わせ | 中盤の人数差、守備人数と相手FW数の差、最終ライン同士の組み合わせ | フォーメーションを数値的な相対関係に変換 |
| 前年の基本スタッツ | シュート、枠内シュート、得点、失点、無失点、パス、ドリブル、クロス、ボール保持率、xG、xGAなど | 新シーズン序盤でも使えるチームの基礎傾向 |
| 前年の守備・運動量 | 被シュート、クリア、タックル、ブロック、インターセプト、空中戦、走行距離、スプリントなど | 守備方法やプレー強度の違い |
| 前年の得点パターン | PK、直接・間接セットプレー、クロス、スルーパス、ドリブルなどからの得点 | どのような形から得点するチームか |
| 前年の攻撃スタイル | 左・中央・右攻撃指数、ショート・ロングカウンター、敵陣・自陣での保持 | 攻撃方向やボールの進め方の特徴 |
| 試合の重要度 | Urgency Score | シーズン進行度と順位・勝点差から見た切迫度 |

左右対称の情報は、原則としてホーム用とアウェイ用を別々に持たせています。例えば`Home_Elo_Before`と`Away_Elo_Before`に加えて、両者の差である`Elo_Diff`も使用します。

フォーメーションは文字列をそのまま使うだけではなく、例えば4-2-3-1ならDF4人・MF5人・FW1人のように分解します。そのうえで、中盤の人数差や「自チームのDF人数 − 相手のFW人数」といった相対特徴量も作成しました。

また、前年のチームスタッツと攻撃スタイルを入れたのは、開幕直後には当年の試合データがほとんど存在しないためです。前年から監督や選手が変わるという弱点はありますが、情報が少ない序盤にチームの初期値として利用できます。

## 3.3 試合前に分かる情報だけを使う

学習データの作成方法そのものは本記事の主題ではないため詳細は省きますが、各行には**その試合のキックオフ前に取得できた情報だけ**を入れています。例えば第10節の予測には、第9節までの順位・勝点・直近成績を使います。

開発途中では試合後に確定する実績観客数と実績収容率が含まれていたため、データリークとして学習・推論の両方から除外しました。天候も取得の安定性とモデルへの寄与を検証したうえで、現在の本番モデルでは使用していません。

xG・AGI・KAGIのようにシーズン中に更新される値は、予測前に取得した値を使用します。過去の時点別データが残っていない期間には取得可能な集計値を推定値として使い、現在は各節前の値をスナップショットとして保存しています。

## 3.4 どの特徴量が効いていたか

本番の期待得点モデルについて、LightGBMのgainベースのFeature Importanceを確認しました。gainは、その特徴量による分岐が学習時の損失をどれだけ改善したかを合計した値です。

ホーム期待得点モデルとアウェイ期待得点モデルでは重要度の合計値が異なるため、それぞれのgainを100%に正規化しました。次のグラフは、2モデルの平均重要度が高かった上位20特徴量を、ホーム・アウェイ別に示したものです。ひし形は両モデルの平均です。

![期待得点モデルのFeature Importance](https://raw.githubusercontent.com/akiokuyama/J1League_score_prediction_site/main/docs/articles/assets/qiita_feature_importance_expected_goals.png)

最も目立ったのは、ホーム・アウェイそれぞれのRolling xG（当季ここまでの1試合平均期待得点）でした。ホームのRolling xGはホーム得点モデル、アウェイのRolling xGはアウェイ得点モデルで特に大きな重要度を持っています。シーズンを通じたチャンスの質を示すxGが、実際の得点予測でも中心的な情報になっていると読めます。

両チームの市場価値差は2モデルで共通して高く、Elo差も上位に入りました。また、前年のスルーパス数、被シュート数、失点数、クロス数なども利用されており、単純な順位だけではなく、チームの攻撃方法や守備傾向が予測へ反映されています。

ただし、Feature Importanceには注意点があります。

- 重要度が高いことは、その特徴量と得点の因果関係を意味しない
- 値が大きいほど得点が増えるのか、減るのかという方向は分からない
- 似た特徴量が複数あると、重要度が分散したり一方へ偏ったりする
- 学習データが変われば重要度も変化する

したがって、このグラフは「モデルが予測の分岐にどの特徴量を多く使ったか」を確認するものです。各特徴量が個々の試合予測をどちらの方向へ動かしたかまで調べる場合は、SHAPなどによる追加分析が必要です。

# 4 旧予測モデルと問題点

以前のモデルは以下の3種類のモデルを別々に学習していました。

| モデル | 目的変数 | アルゴリズム |
| --- | --- | --- |
| 得点モデル | Home Goals・Away Goals | `MultiOutputRegressor(LGBMRegressor)` |
| 勝敗モデル | Home・Draw・Away | `LGBMClassifier` |
| 得点差モデル | Home Goals - Away Goals | `LGBMRegressor` |

最後に、3つの出力ができるだけ整合するようにスコア候補を補正していました。

しかし、独立して学習したモデルは必ずしも同じ答えを出しません。

例えば、以下のような結果が発生します。

- 期待得点：ホーム1.4、アウェイ1.1
- 勝敗分類器：アウェイ勝利が最大
- 得点差モデル：ホーム寄り
- 最終表示スコア：1-0

この場合、表示スコアはホーム勝利なのに、勝敗確率はアウェイ勝利になります。

後処理を複雑にして整合性を取るよりも、予測スコアと勝敗確率を同じ確率分布から計算する方針へ変更しました。

# 5 期待得点からスコア分布を作る

## 5.1 LightGBMで期待得点を予測

まずLightGBM回帰モデルを使って、ホームとアウェイの期待得点を予測します。

特徴量ベクトルを$\mathbf{x}$、ホーム期待得点を$\lambda_H$、アウェイ期待得点を$\lambda_A$とすると、以下の2つの関数を学習するイメージです。

```math
\lambda_H = f_H(\mathbf{x}), \qquad
\lambda_A = f_A(\mathbf{x})
```

実装では`MultiOutputRegressor`を利用し、2つの`LGBMRegressor`を学習します。

```python
from lightgbm import LGBMRegressor
from sklearn.multioutput import MultiOutputRegressor

model = MultiOutputRegressor(
    LGBMRegressor(
        objective="regression",
        random_state=42,
    )
)

model.fit(
    X_train,
    y_train[["Home_Goals", "Away_Goals"]],
)

expected_goals = model.predict(X_test)
home_lambda = expected_goals[:, 0]
away_lambda = expected_goals[:, 1]
```

## 5.2 ポアソン分布で得点確率を計算

チームの得点数がポアソン分布に従うと仮定します。

期待得点を$\lambda$、実際の得点を$k$としたとき、$k$得点する確率は以下です。

```math
P(X=k)=\frac{e^{-\lambda}\lambda^k}{k!}
```

ホームとアウェイの得点を独立と仮定すると、スコア$(h,a)$の確率は以下になります。

```math
P(H=h,A=a)
=
\frac{e^{-\lambda_H}\lambda_H^h}{h!}
\frac{e^{-\lambda_A}\lambda_A^a}{a!}
```

勝敗確率は、全スコアの確率を結果カテゴリごとに足し合わせます。

```math
P(\mathrm{HomeWin})=\sum_{h>a}P(h,a)
```

```math
P(\mathrm{Draw})=\sum_{h=a}P(h,a)
```

```math
P(\mathrm{AwayWin})=\sum_{h<a}P(h,a)
```

予測スコアは$P(h,a)$が最大になる組み合わせ、スコア候補Top 5は確率が高い順の5組とします。

## 5.3 Pythonによる実装

以下は、実際の処理を簡略化したコードです。

```python
import math


def poisson_pmf(k: int, lam: float) -> float:
    return math.exp(-lam) * lam**k / math.factorial(k)


def predict_score_distribution(
    expected_home_goals: float,
    expected_away_goals: float,
    max_goals: int = 8,
    top_n: int = 5,
):
    home_lambda = max(float(expected_home_goals), 0.05)
    away_lambda = max(float(expected_away_goals), 0.05)

    candidates = []
    for home_goals in range(max_goals + 1):
        for away_goals in range(max_goals + 1):
            probability = (
                poisson_pmf(home_goals, home_lambda)
                * poisson_pmf(away_goals, away_lambda)
            )

            if home_goals > away_goals:
                result = "home_win"
            elif home_goals == away_goals:
                result = "draw"
            else:
                result = "away_win"

            candidates.append(
                {
                    "score": f"{home_goals}-{away_goals}",
                    "result": result,
                    "probability": probability,
                }
            )

    # 0〜8得点の有限範囲で確率和が1になるように正規化
    total = sum(item["probability"] for item in candidates)
    for item in candidates:
        item["probability"] /= total

    result_probabilities = {
        result: sum(
            item["probability"]
            for item in candidates
            if item["result"] == result
        )
        for result in ("home_win", "draw", "away_win")
    }

    candidates.sort(
        key=lambda item: item["probability"],
        reverse=True,
    )

    return {
        "predicted_score": candidates[0]["score"],
        "result_probabilities": result_probabilities,
        "top_scores": candidates[:top_n],
    }
```

## 5.4 予測スコアと勝敗確率が異なる理由

この方式でも、「予測スコアは1-1だが、勝敗確率はホーム勝利が最大」という結果は発生します。

これは矛盾ではありません。

予測スコアの1-1は、**1つのスコアセル**として最も確率が高いことを意味します。一方、ホーム勝利確率は1-0、2-0、2-1、3-0など、ホームが勝つ全スコアの合計です。

```text
1-1の確率                 = 12%

ホーム勝利確率
= P(1-0) + P(2-0) + P(2-1) + ...
= 46%
```

単一スコアと結果カテゴリの合計では比較する単位が異なります。

UIでは誤解を避けるため、勝敗確率トップが45%未満、または上位2カテゴリの差が10ポイント未満なら「拮抗」と表示しています。

# 6 モデルの比較と評価

## 6.1 時系列データの検証方法

通常のランダムな交差検証では、未来の試合が学習データへ混ざる可能性があります。そのため、モデル選択にはwalk-forward評価を使用しました。

```text
2021〜2022年で学習 → 2023年を評価
2021〜2023年で学習 → 2024年を評価
2021〜2024年で学習 → 2025年を評価
2021〜2025年＋特別リーグ前半で学習 → 特別リーグ後半を評価
```

各評価期間より未来のデータは学習に使用しません。

時系列予測では、データ分割だけを時系列にしても、特徴量作成時に未来情報が入っていれば意味がありません。Point-in-Time特徴量と時系列分割の両方が必要です。

## 6.2 L2回帰とPoisson回帰の比較

L2回帰とPoisson回帰は、どちらも試合の特徴量から期待得点を予測する回帰モデルです。違いは、学習時に「予測の間違いをどのように評価するか」にあります。

### L2回帰

L2回帰は、予測値と実際の値の差を二乗した**二乗誤差**を小さくするように学習します。実際の得点を$y_i$、予測した期待得点を$\hat{y}_i$とすると、損失は次のように表せます。

```math
L_{\mathrm{L2}}
=
\frac{1}{n}\sum_{i=1}^{n}(y_i-\hat{y}_i)^2
```

例えば、実際は1得点だった試合を1.5得点と予測した場合の誤差は$0.5^2=0.25$、3得点と予測した場合は$2^2=4$です。大きく外した予測ほど強く罰せられます。

得点を通常の連続値として扱うシンプルな方法で、LightGBMでは`objective="regression"`を指定します。出力は1.37のような小数であり、「1.37点取る」という意味ではなく、多数の同条件の試合を考えたときの平均的な得点数、つまり期待得点を表します。

### Poisson回帰

Poisson回帰は、得点数を0、1、2、3……と数える**カウントデータ**として扱います。予測値$\hat{y}_i>0$をポアソン分布の平均とみなし、観測された得点が起きる確率を高くするように学習します。

定数項を除いた損失は、概ね次の形です。

```math
L_{\mathrm{Poisson}}
=
\sum_{i=1}^{n}
\left(
\hat{y}_i-y_i\log\hat{y}_i
\right)
```

LightGBMでは`objective="poisson"`を指定します。一般的な線形のPoisson回帰とは異なり、今回比較したのは**決定木を使うLightGBMをPoisson損失で学習したモデル**です。得点が負にならないことや、低得点が多いサッカーのデータと考え方が合いやすい点が利点です。

ここで注意したいのは、「Poisson回帰」と5章の「ポアソン分布によるスコア確率計算」は別の処理だという点です。

```text
回帰モデル：特徴量から期待得点 λ を予測する
    ├── L2損失で学習する方法
    └── Poisson損失で学習する方法

スコア分布：予測された λ から0点、1点、2点……の確率を計算する
```

現在の本番モデルはL2回帰で期待得点を求め、その期待得点をポアソン分布へ渡しています。したがって、Poisson回帰を採用しなかったからといって、スコア確率の計算でポアソン分布を使っていないわけではありません。

期待得点モデルとして以下の5種類を比較しました。

- L2 LightGBM回帰
- L2 75% + Poisson 25%
- L2 50% + Poisson 50%
- L2 25% + Poisson 75%
- Poisson LightGBM回帰

ブレンドモデルでは、L2回帰の期待得点を$\lambda_{\mathrm{L2}}$、Poisson回帰の期待得点を$\lambda_{\mathrm{P}}$、Poisson側の重みを$w$として、次のように平均します。

```math
\lambda
=
(1-w)\lambda_{\mathrm{L2}}
+w\lambda_{\mathrm{P}}
```

主要な結果は以下です。

| 候補 | 勝敗Accuracy | 勝敗Log Loss |
| --- | ---: | ---: |
| L2 | 45.38% | 1.06544 |
| L2 75% + Poisson 25% | 45.56% | 1.06543 |
| L2 50% + Poisson 50% | - | 1.06585 |
| L2 25% + Poisson 75% | - | 1.06671 |
| Poisson | - | 1.06803 |

L2 75%・Poisson 25%のブレンドがわずかに良い結果でしたが、Log Lossの差は約0.00001でした。

差が実質的にない場合は、より単純なモデルを採用する基準にしていたため、L2 LightGBM回帰を本番モデルにしました。

得点がカウントデータであることだけを考えるとPoisson回帰が自然に見えます。しかし、最終的な評価対象は期待得点そのものではなく、その期待得点から作った勝敗確率です。理論上の自然さだけでなく、最終指標を時系列評価して決める必要があります。

## 6.3 温度スケーリング

温度スケーリングは、モデルが出した確率の**自信の強さ**を調整する確率校正の方法です。勝敗の順番や元のモデルを作り直すのではなく、ホーム・引き分け・アウェイの確率差を、1つのパラメータ$T$で広げたり縮めたりします。

例えば、モデルが次の確率を出したとします。

```text
ホーム勝利 70% / 引き分け 20% / アウェイ勝利 10%
```

しかし過去の検証で「70%と予測した試合が、実際にはそれほど当たっていない」と分かれば、モデルは自信過剰です。この場合、最大確率を少し下げ、残りへ確率を配り直します。反対に、予測確率の差が実際より小さすぎる場合は、最大確率をより高くします。

未校正確率を$q_k$、温度を$T$とすると、校正後確率$q'_k$を以下で計算します。

```math
q'_k=\frac{q_k^{1/T}}{\sum_j q_j^{1/T}}
```

$T>1$なら確率分布が平らになり、$T<1$なら確率差が大きくなります。

例えば上記の70%・20%・10%に$T=2$を適用すると、約52%・28%・20%となり、予測する勝敗の順番は保ったまま確率が控えめになります。$T=1$なら元の確率から変化しません。

この$T$は人が感覚で決めるのではなく、学習に使っていない検証予測に対するLog Lossが小さくなるように推定します。新しい試合特徴量を追加する方法ではなく、モデルが出した確率に対する後処理です。

全Out-of-Fold予測から求めた温度は約1.103でした。しかし、過去の予測だけで温度を推定する時系列評価では、以下のように悪化しました。

| 指標 | 未校正 | 時系列校正後 |
| --- | ---: | ---: |
| Log Loss | 1.06544 | 1.06762 |
| Brier Score | 0.64311 | 0.64481 |

そのため、校正処理自体は実装しましたが、本番では$T=1.0$として未適用にしています。

新しい手法を実装したからといって、必ず本番で使う必要はありません。時系列評価で悪化した変更は採用しないようにしました。

## 6.4 評価結果

2026年百年構想リーグのうち、5月1日以降の71試合をホールドアウトして評価しました。

| モデル | 勝敗Accuracy | 勝敗Log Loss |
| --- | ---: | ---: |
| 旧勝敗分類器 | 38.03% | 1.1997 |
| 新スコア分布モデル | 49.30% | 1.0478 |

新モデルの完全スコア一致率は16.90%でした。

予測精度の確認にはAccuracyだけでなく、Log LossとBrier Scoreも使用します。

- Accuracy：最大確率の勝敗カテゴリが当たった割合
- Log Loss：正解カテゴリへ低い確率を出すほど大きく罰する
- Brier Score：予測確率と実際の結果の二乗誤差

サッカーの予測では「ホーム勝利51%、引き分け25%、アウェイ勝利24%」のような接戦が多くなります。最大確率のカテゴリだけを見るAccuracyでは、確率予測の良し悪しを十分に評価できないため、確率指標も必要です。

なお、評価対象は71試合と少ないため、49.30%という結果が新シーズンでも維持されるとは限りません。通常年だけで学習したモデルもシャドーモデルとして残し、本番モデルと同じ試合を並行予測します。

# 7 10,000回の最終順位シミュレーション

残り全試合のスコア分布を使い、リーグ終了までを10,000回シミュレーションします。

1回のシミュレーションでは、各試合についてスコア分布から1つのスコアをランダムに選び、勝点、得点、失点を加算します。

```python
import numpy as np

rng = np.random.default_rng(202_627)

sampled_index = rng.choice(
    len(score_probabilities),
    size=10_000,
    p=score_probabilities,
)

sampled_scores = score_values[sampled_index]
home_goals = sampled_scores[:, 0]
away_goals = sampled_scores[:, 1]

home_points = (
    (home_goals > away_goals) * 3
    + (home_goals == away_goals)
)
```

各シミュレーションの順位は、勝点、得失点差、得点数の順に決めます。全て同じ場合のみ、シード付き乱数で順位を決定します。

10,000回の結果から、以下を集計します。

- 期待勝点
- 予測順位
- 順位の10〜90パーセンタイル
- 優勝確率
- Top 3確率
- 下位3確率

予測結果は実行日時ごとに保存します。シーズン終了後に各時点の予測と最終順位を比較し、何節から順位予測が安定したかを検証できるようにしています。

# 8 アプリへの組み込み

## 8.1 JSONをモデルとUIの境界にする

推論結果は以下のようなJSONとして保存します。

```json
{
  "home_team": "チームA",
  "away_team": "チームB",
  "expected_home_goals": 1.42,
  "expected_away_goals": 1.08,
  "predicted_score": "1-1",
  "result_probabilities": {
    "home_win": 0.46,
    "draw": 0.25,
    "away_win": 0.29
  },
  "score_candidates": [
    {"score": "1-1", "probability": 0.12},
    {"score": "1-0", "probability": 0.11}
  ]
}
```

モデル側はJSONの生成まで、UI側はJSONの表示だけを担当します。

予測処理と画面表示を分離することで、StreamlitとPWAで同じデータを使えます。また、モデルやスクレイピング処理で一時的なエラーが発生しても、最後に正常生成されたJSONを表示できます。

## 8.2 StreamlitとPWA

Web版はStreamlitで作成しました。

Streamlitでは、一覧、試合詳細、過去結果、最終順位予測を表示します。チームや節による絞り込み、スコア候補、得点者候補など、詳細な情報を確認できます。

スマートフォン向けには、GitHub Pages上で動くPWAを作成しました。

- Service Workerによるキャッシュ
- `manifest.webmanifest`によるホーム画面追加
- `localStorage`によるマイチーム・テーマ設定の保存
- スマートフォン向け順位予測カード
- 前回取得データのオフライン表示

ネイティブアプリを作らなくても、PWAであればブラウザからホーム画面へ追加し、アプリに近い体験を提供できます。

## 8.3 GitHub Actionsによる自動更新

予測は毎週水曜日、試合結果は毎週月曜日に更新します。

```yaml
on:
  schedule:
    - cron: "0 22 * * 2"  # 水曜 07:00 JST

jobs:
  update-predictions:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      - name: Install dependencies and test
        run: |
          pip install -r requirements.txt
          python -m pytest

      - name: Build predictions
        run: |
          python scripts/run_competition_pipeline.py \
            --competition-key 2026_27_j1
          python scripts/build_standings_forecast.py
          python scripts/validate_prediction_outputs.py
```

生成ファイルを検証し、問題がなければGitHub ActionsのBotが予測JSONをコミットします。

結果更新と予測更新のWorkflowを分けています。試合直後の結果更新では、過去の予測ファイルが書き換わっていないことをハッシュ値で検証します。

これにより、実際の結果を取得した後で過去予測が再計算されることを防いでいます。

# 9 AIを使った開発で感じたこと

アプリ開発には生成AIを使用しました。

私は画面やエラーログを確認して、「どのような状態にしたいか」「現在の挙動の何がおかしいか」を自然言語で説明し、AIがコードを実装しました。

特に役立ったのは以下です。

- 既存コード全体から原因を調査する
- テストを追加してバグを再現する
- StreamlitとPWAの表示を揃える
- GitHub Actionsの実行順序を整理する
- モデルの代替案を比較する
- 実装内容をドキュメントへ残す

一方、AIが書いたコードをそのまま採用すると、以下の問題が発生します。

- 試合後にしか分からない特徴量を使う
- 時系列データをランダム分割する
- 複数モデルの出力が矛盾する
- ローカルでは動くがGitHub Actionsでは動かない
- UI修正で別画面を壊す

AIを使ってコードを書く速度は大きく上がりましたが、何を正しい状態とするかは人間が決める必要があります。

今回の開発では、「コードを書く能力」よりも以下が重要でした。

- 予測時点で取得可能なデータを定義する
- 適切な評価方法を選ぶ
- 予測結果の見え方に違和感を持つ
- テストとログでAIの実装を検証する
- 採用しなかった案も記録する

# 10 今後の改善

新シーズン開始後は以下を確認します。

- 毎節の予測前スナップショットが保存されているか
- 本番モデルと通常年だけで学習したシャドーモデルの比較
- Accuracy、Log Loss、Brier Scoreの推移
- 予測スコアが1-1へ集中していないか
- 温度スケーリングを再評価するべきか
- 特別リーグのデータ追加が新シーズンでも有効か
- 最終順位予測が何節から安定するか

モデルを作成した時点のオフライン評価だけで、モデルの良し悪しを決めることはできません。

特に今回のように、大会形式が通常年と異なるデータを追加した場合は、本番運用中の継続評価が必要です。そのため、通常年モデルをシャドーモデルとして残し、予測時点の特徴量と予測結果を保存する構成にしました。

機械学習をアプリへ組み込む場合、モデルのアルゴリズムだけでなく、データの時点管理、予測履歴、切り戻し、監視まで含めて設計することが重要だと感じました。
